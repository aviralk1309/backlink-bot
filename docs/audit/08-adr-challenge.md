# ADR challenge

## Executive summary

1. This review reread ADRs 0001–0024 plus the 0000 template and index; the template is not a decision (`docs/adr/0000-template.md:1-8`; `docs/adr/README.md:3-32`).
2. ADRs 0001–0010 describe mostly real mechanisms, but defer alternatives, consequences, and reversibility to an untracked “MVP plan section 0.5” (`docs/adr/0001-modular-monolith.md:3-7`; `docs/adr/0010-search-provider-interface.md:3-7`; `git ls-files | rg -i 'mvp|plan'`).
3. Postgres queueing still fits a small internal workload, but claim selection already takes about 499 ms on 200,000 pending rows; a million-row report takes 6.6 seconds (D-01, D-02).
4. Direct Postgres access and many RPCs make atomic state transitions possible, while business policy is spread across Python, SQL, and Next.js (`apps/worker/src/worker/engine/runner.py:29-69`; `supabase/migrations/20261028040000_m6_review_actions.sql:35-100`).
5. ADR 0005's “stored results never rewritten” is false for explicit rescore; configuration snapshots themselves still exist (`docs/adr/0005-config-versioning.md:3`; `apps/worker/src/worker/scoring/rescore.py:19-64`).
6. ADR 0006's six named pipeline stages are conceptual, not six durable database states (O-06; `supabase/migrations/20261013150133_m3_opportunities.sql:60-75`).
7. ADR 0023's ban on displacing a Ready row is directly contradicted by the later queue migration and its tests (O-03; `supabase/migrations/20261104020000_quality_ready_queue.sql:53-72`).
8. ADR 0011 deliberately deferred hosting and chose logs/events only; an untracked VPS draft now exists, while release and alert ownership remain absent (O-07, I-01, I-03).
9. Scoring method has an ADR, but its weights are uncalibrated on real prospects; auth, tenancy, retention, and scraping governance lack equivalent decision records (P-02, P-08, P-10).
10. New findings: **BLOCKER 0, HIGH 2, MEDIUM 1, LOW 0**. Existing O-03/O-06/O-07 and the cited product, backend, database, and infra findings are not repeated.

## Devil's advocate: three big bets

### Postgres as the queue

**Strongest case against:** the same database serves queue claims, RLS-protected user reads, review writes and reports. A 200k-pending claim already grouped 2,000 domains and took 499 ms; a 1M-result report took 6.6 s on disposable data (D-01/D-02). Increasing worker replicas also raises pool demand (`apps/worker/src/worker/config/settings.py:24-32`; `apps/worker/src/worker/db/pool.py:8-14`). Poison work reaches a failed status but has no operator dead-letter lane (B-08).

**Starting over:** if the target were a multi-tenant, always-on product with million-row jobs, use Postgres as the source of truth plus a transactional outbox, and a managed queue with delayed retries/dead-letter delivery for execution. Keep job budgets, idempotency keys, lease/fencing state and result writes in Postgres. For the present single-team pilot, I would still start with Postgres, but use one clearly indexed work table and a measured claim SLO instead of multiple queue-like tables. The choice hinges on measured pending volume, claim latency, DB load and operational staffing—not on a belief that brokers are inherently better.

**Path from here:** first fix and benchmark the current hot claim query (D-01), record oldest-work age/attempt outcomes, and establish an idempotent stage key. Then write an outbox row in the same transaction that creates work, publish it to the new queue, and run a shadow consumer that observes but does not mutate results. Switch one stage (search is the hardest because it spends money) only after duplicate/crash tests prove fencing and credit reservation; retain the Postgres claim path until the new consumer's outcomes and backlog age agree. Roll back consumers, not durable work rows. B-04 makes paid-call replay a gate, not a footnote.

### SQL-heavy business logic in RPCs

**Strongest case against:** the database is both state machine and API: job transitions, queue admission, review, report aggregation and search-budget claims live in PL/pgSQL, while ranking/filter/scoring live in Python. Rules can drift when Next validation, Python and SQL each encode a slice (B-09; `supabase/migrations/20261010182546_m2_job_lifecycle.sql:1-20`; `supabase/migrations/20261028040000_m6_review_actions.sql:35-100`; `apps/worker/src/worker/scoring/engine.py:55-150`). Long rescore/import transactions and large report RPCs make a policy change a database rollout (B-02/B-03/D-02).

**Starting over:** keep RLS, constraints, unique keys, budget reservations and short atomic transition RPCs in Postgres; put evolving ranking, source selection and report composition in one versioned application service. A single-team prototype can use the existing Next/Python runtimes rather than adding a separate service immediately. The split depends on whether a rule must remain true under every client/concurrent worker (DB) or is a tunable product policy (application). There is no ADR setting that boundary today.

**Path from here:** inventory each RPC's invariants and callers, freeze current behavior with pgTAP/integration fixtures, and extract one policy at a time behind a versioned RPC response. Compute old/new outcomes in shadow on the same snapshots, compare by reason code and job type, then make the application policy authoritative while DB constraints still reject unsafe transitions. Keep old RPC signatures through one compatible deploy window; remove them only after callers and historical jobs are migrated. Do not move permission or spend checks into UI-only code.

### Local-first hosting

**Strongest case against:** an always-on search/check pipeline needs the worker, database, Storage and mail to remain available when the developer laptop is asleep. ADR 0011's error-tracking choice provides no paging route; the tracked Compose file runs only a local worker, and the proposed VPS deployment is still untracked (I-01/I-03; `docs/adr/0011-local-first-hosting.md:1-5`; `docker-compose.yml:1-9`; `git status --short`). Backup recovery is untested (D-04).

**Starting over:** for an external always-on service, choose separate staging and production Supabase projects, a managed web runtime and a managed worker container in the same region, with central logs, alerts and a tested restore target. For a private pilot operated by one person, a single host can be acceptable only with explicit downtime tolerance and a human owner. The reversal trigger is first promised availability or paid customer data, not a vague future milestone.

**Path from here:** decide whether the untracked VPS/Tunnel draft is the intended first release; record that in a replacement ADR. Make environment/secrets/IaC and image digests reproducible, rehearse migrations and restore in staging, define health checks for DB-backed job execution, and alert on worker heartbeat plus oldest claimable work. Promote a tested image digest, keep the prior digest for rollback, and deploy compatible migrations before code that requires them. Do not call a successful `docker compose config` a deployed service (I-01/D-04).

## Findings

### [A-01] Foundational ADR tradeoffs point to a missing plan
- Severity: MEDIUM
- Type: DOC-DRIFT
- Area: Process
- Evidence: `docs/adr/0001-modular-monolith.md:3-7`; `docs/adr/0002-postgres-queue.md:3-7`; `docs/adr/0010-search-provider-interface.md:3-7`; `git ls-files | rg -i 'mvp|plan'` returned only the quality plan, query-plan files and tests, not the cited MVP plan.
- Why it matters: The repo can show what was built, but not why the first ten architectural choices beat their alternatives or what cost/scale assumptions made them reversible. Their accepted status is therefore a weaker decision record than it appears.
- Recommendation: Recover and link the original plan if it exists; otherwise replace the missing references with one paragraph per ADR naming the rejected alternative, current assumption and measurable reversal trigger. Effort S.
- Confidence: High

### [A-02] No decision assigns business rules to SQL or application code
- Severity: HIGH
- Type: GAP
- Area: Backend/API
- Evidence: `supabase/migrations/20261010182546_m2_job_lifecycle.sql:12-20`; `supabase/migrations/20261028040000_m6_review_actions.sql:35-100`; `supabase/migrations/20261030010000_m7_report_metrics.sql:24-107`; `apps/worker/src/worker/checks/auto_filter.py:1-119`; `apps/worker/src/worker/scoring/engine.py:55-150`; `apps/worker/src/worker/engine/runner.py:29-69`.
- Why it matters: Each layer is locally reasonable, but there is no rule for where the next budget, ranking, or lifecycle policy belongs. Duplicate validation and versioned RPC changes can silently diverge across SQL, Python, and Next.js; B-09 is one concrete instance.
- Recommendation: Record a boundary ADR: database owns authorization, atomic invariants and durable state; Python owns versioned check/score/query policy; Next owns presentation and preflight validation. Add one cross-layer behavior fixture for each rule implemented twice and an RPC compatibility rule for deploys. Effort M.
- Confidence: High

### [A-03] Launch-boundary decisions are left implicit
- Severity: HIGH
- Type: GAP
- Area: Process
- Evidence: `docs/adr/0011-local-first-hosting.md:1-5`; `docs/adr/0004-permission-catalog.md:1-7`; `docs/adr/0012-roles-manage-is-admin-equivalent.md:3-16`; `supabase/migrations/20261010181654_m2_jobs_rls.sql:82-102`; `apps/web/src/features/auth/actions.ts:47-84,88-123`; `docs/adr/0018-origin-robots-cache.md:7-50`; `docs/adr/0022-deterministic-scoring-and-explicit-rescore.md:7-40`; `git ls-files docs/adr` shows no separate tenant, retention, hosted operation or scraping-governance ADR.
- Why it matters: The current single-team, local-first assumptions may be defensible, but the repo does not define the point at which external users, always-on operation, contact-data collection or score claims become supported. P-08/P-10/I-01/P-02 record the implementation and product risks; this finding is about the absent decision gates.
- Recommendation: Before external use, record four short accepted decisions: supported tenant boundary, data collection/retention and takedown policy, hosted operating model with owner, and empirical scoring acceptance gate. Amend ADR 0011/0022 instead of inventing duplicate ADRs for decisions they already partially cover. Effort M.
- Confidence: High
